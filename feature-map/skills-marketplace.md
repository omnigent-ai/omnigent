# Skills marketplace

Settings → Skills lets a user browse repositories of skills, install the ones they want, and have them offered in every new session's slash menu on any host or sandbox. Administrators manage which repositories are browsable; anyone can preview a GitHub repository by URL. Off by default, behind the `skills_marketplace` feature.

## Sub-features

- `skill-sources`: administrators add a GitHub repository (`owner/repo`, `host/owner/repo` or URL, optional branch or tag, optional directory from a `/tree/<ref>/<dir>` link) to the browse list and remove it again; removing a source leaves installed skills in place. The local single user of `omnigent server` (the reserved `local` user, created as an admin) is an administrator.
- `skill-source-directory`: a source's directory is its catalog root, so a monorepo's team folders are separate sources; a link to one skill's directory lists that skill. Clones are partial and sparse: a catalog checks out only manifests under the directory, an install only the chosen skills.
- `skill-catalog`: a source's skills, with name, description, plugin tag for marketplace plugins, path and commit, searchable; skills the user already installed show Installed instead of a button; entries the marketplace could not read are listed as skipped.
- `skill-preview-url`: previewing any GitHub repository by URL shows its catalog without adding it as a source, and installs from it the same way.
- `skill-install-scope`: a user installs for themselves; an administrator can install for everyone.
- `installed-skills`: the Installed tab lists each skill with its source, ref, commit and scope, with enable/disable, Update (refetch at the same ref), Remove behind a confirmation, and a SKILL.md preview.
- `skills-in-session`: an enabled installed skill appears in the new-session slash menu and is usable in the session, on a connected host and in a managed sandbox, for every harness; the agent spec's `skills:` filter still applies, a bundled skill of the same name wins, and a skill whose frontmatter says `user-invocable: false` is delivered but never listed.
- `skill-policy`: the server config's `skills_marketplace:` block binds admins and the local user alike: `sources` are seeded at startup and shown with a Config tag nobody can remove, `allowed_sources` globs refuse other repositories on every fetch path and stop serving skills already installed from them, `allow_url_install: false` hides Add from URL and refuses installs from unlisted repositories, and `credentials` send an operator token to matching private repositories only.
- `skill-enterprise-hosts`: a URL on a GitHub Enterprise Server host the server knows (`GH_HOST`, `OMNIGENT_GIT_PROVIDER_GITHUB_HOSTS`, gh's signed-in hosts) is accepted with its host kept in the clone URL and label; an unknown host is refused rather than rewritten to github.com.

## How to get to it (user POV)

- Settings → Skills → Browse: pick a source on the left, search, Install on a card; or paste a repository under Add from URL and Preview skills.
- Settings → Skills → Installed: toggle, Update, Remove, or click a name to read its SKILL.md.
- New session: type `/` in the composer; installed skills are listed with their repository as the source.
- Feature off: the Skills entry is absent from Settings and the routes answer 404.

## Gotchas

- Only GitHub repositories are accepted; a GitLab or arbitrary git URL is rejected with a message, not cloned. A GitHub Enterprise host must be one the server knows, or its URL is refused.
- The `skills_marketplace:` config block overrides admin rights: a repository outside `allowed_sources` is refused even for an admin, and skills already installed from it stop being served once the policy tightens. The allowlist fails closed: a malformed block or a list with no usable entry refuses every repository; only an absent key or an explicit empty list means any.
- A credential token is only ever sent to a repository that matches both `allowed_sources` and its `match`, for one clone of that origin, never stored or forwarded; an unset `token_env` is logged and the clone proceeds anonymously.
- Personal installs are private: a session's bundle carries them only when the runner (managed host) or the owner fetches it; a shared reader or editor downloading the bundle gets the agent's own files, and the session menu shows the owner's installs, never the caller's.
- Each user and Everyone hold at most 200 installed skills, and 200 MB and 4,000 files of enabled skills unpacked (two fifths of what a runner unpacks), checked at install, update and enable time under one lock per owner, so a later session launch cannot fail on size; an install of several skills is all or nothing; the delivery backstop fails with a message rather than dropping skills silently, including when the agent's own files push the merged bundle past the runner's limits.
- A child-agent session gets installed skills under `agents/<dir>/skills/`, where the runner reads the child's spec, under the child's filter; the pre-launch menu shows an installed skill over a host skill of the same name, and a bundled skill over both.
- A clone is killed past 500 MB on disk, 20,000 entries or 300 seconds (operator-configurable under `skills_marketplace.limits`), and a finished checkout over either budget is refused; each account has one fetch in flight at a time (a second answers 409).
- A skill directory name must be a valid bundled skill name (`[a-z0-9-]`, at most 64 characters); others are listed as skipped, since one invalid name fails the runner's whole spec.
- Each owner's totals live on a lock row and every write adjusts them in its transaction, so a quota check never scans rows and holds on MySQL's repeatable-read snapshot too.
- A session's owner comes from the conversation store's owner lookup; on a multi-user server a session whose owner cannot be resolved gets nobody's installs rather than the local user's or everyone's.
- A skill's frontmatter is parsed with YAML anchors refused and a non-scalar name or description rejected, so an untrusted repository cannot expand a small manifest into a large structure; the entry is skipped with a note.
- An install writes its tarballs before its rows: a later failure drops the objects that request created, and an object an earlier row already points at is kept.
- A list page's `last_id` is an opaque cursor carrying the last row's position, so removing that row between two pages neither fails nor truncates the next one; a cursor the server did not issue answers 400.
- The content route answers 404 when a skill's stored copy is gone and 409 when it cannot be read, both saying to update or remove the skill; an update that loses a race with a removal drops the object it had stored.
- Browse: **Refresh** re-fetches a source's catalog past the server's cache; a source removal that is refused says why beside the source; installing from a URL preview marks the card without re-fetching; the slash menu names the repository an installed skill came from.
- A ref must be a branch or tag. A commit SHA cannot be shallow-cloned by name and fails with a hint.
- A running session keeps the skills it started with; installs show up on the next session start.
- Lists are paged (50 per page by default, 200 at most); Settings shows Load more when a page follows.
- When a user and the org both install the same name, the user's copy wins for that user.
- Turning the feature off keeps installed rows but stops every reader: the routes, discovery and served bundles.
- Catalogs are cached for ten minutes per source and ref; the Refresh button on a source's catalog (`?refresh=true`) re-fetches after pushing to the repository.
- Marketplace plugins whose source is another repository are reported under "skipped", not followed.
